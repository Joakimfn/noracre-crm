# Norwegian, English and French

The CRM interface and public website support Norwegian Bokmål (`nb`), English (`en`) and French (`fr`). The recruiter presentation at `/portfolio` starts in English and includes a separate, fictional-data CRM demo.

## Language selection

- Public website and CRM login: Cloudflare's trusted `request.cf.country` sets the default. Norway, Sweden and Denmark use Norwegian; **every other country, including France and Belgium, uses English**. Missing or unrecognised country metadata also uses English. Browser-language and client-supplied country headers are not used.
- A valid `?lang=nb`, `?lang=en` or `?lang=fr` overrides saved preferences and geography. Invalid language queries are ignored. Manual choices are saved in the existing `noracre-language` cookie for one year. Public pages save them on the server too, so JavaScript is not required. French remains available as a manual choice.
- Internal public links preserve the language in all three languages, including Norwegian. CRM login and legal links carry it across host-only cookies on separate subdomains. An incoming language link or a choice on the login screen overrides older CRM organisation preferences and is saved for the first organisation after login.
- CRM: **My settings → Language** offers all three languages. Existing manual preferences stay in each organisation's local-storage entry. Without a manual choice, the organisation's home-country rule is unchanged: Norway uses Norwegian, France and Belgium use French, and other countries use English. Later organisation switches use their own saved choice or company default.
- The active CRM language is stored separately in the session-only `noracre-language-active` cookie. Automatic organisation defaults do not overwrite a persistent manual choice. This keeps CRM legal pages and reloads consistent. A new choice removes a stale `lang` query while preserving other query parameters and the fragment. In-memory preferences keep manual choices stable if local storage is blocked.
- The Worker resolves each page request before the root layout renders, supplying the same effective language to HTML, legal metadata and React. There is no process-wide mutable locale. Personalised page responses use `Cache-Control: private, no-store` so a visitor does not receive another visitor's language from a shared cache. APIs and static assets retain their existing behaviour.
- Language selection is a device preference. It does not change the user profile DTO, trigger profile autosave or need a database migration.

## Translation APIs

- `createI18n(locale)`, `useI18n()` and the typed `messages/nb.ts`, `messages/en.ts` and `messages/fr.ts` catalogues cover navigation, common messages, plurals, dates and numbers. All catalogues have matching keys and placeholders.
- `UiText` and `useUiTranslation().ui()` translate developer-authored interface copy using `ui-en.json` or `ui-fr.json`. Numeric placeholders such as `{0}` interpolate values once. React escapes rendered output.
- `localizePublicHtml()` translates the website's static text and selected accessible attributes, using `site-en.json` or `site-fr.json` and the shared form catalogue. URL identifiers, input values and enquiry payloads remain unchanged. JSON for client messages is escaped before insertion into HTML.
- Unknown strings are kept as received. New backend/provider error messages should be added to the UI dictionary when appropriate. Never pass customer names, notes, subjects or other user-authored content through the UI translator.

## Stable business data

Database role/status/activity values stay Norwegian. Translate their display labels, never their identifiers. For example, an English **Meeting** button still creates an activity with `kind: 'Møte'`, and a **User** label still corresponds to `role: 'Bruker'`. Authorization checks and select values use the original identifiers.

Language does not convert currency or change billing rules. Prices remain NOK and reporting instants use Europe/Oslo. Calendar dates retain their day; date pickers accept day.month.year in all languages, with translated months and accessible navigation. Customer-entered content, historical records, saved offer/email templates and source business-register industry names retain their original language. New system-generated quote drafts and templates use the current language. French register employee intervals remain stored as published and are only formatted for display. Local numeric filters include overlapping intervals and never invent an exact employee count. System billing CSV exports use translated column headings.

## Portfolio and demo

`app/portfolio` is an unauthenticated presentation of the project and its sales rationale. Opening the demo supplies `createDemoRuntime().request` through `CrmApiProvider`; the real tenant API is not used. Each demo has its own in-memory data. Email sending, publishing, account connections and external lookups remain blocked by the existing demo runtime. The application repository remains private.

## Verification

Run the focused language and demo tests with:

```sh
node --test tests/language-preference.test.mjs tests/bilingual-portfolio.test.mjs tests/i18n.test.mjs tests/french-crm.test.mjs tests/french-public-site.test.mjs tests/french-legal-auth.test.mjs tests/french-import.test.mjs tests/country-language.test.mjs tests/visitor-language-runtime.test.mjs tests/demo-crm.test.mjs tests/public-website.test.mjs tests/module-showcase.test.mjs
```

Run the normal install/build and remaining regression checks using the repository's locked dependencies before deployment. Language tests cover request isolation, initial server language, persistence, escaping, form identifiers, canonical activity identifiers, unchanged prices, administrator controls and demo isolation. Existing customer content is preserved. The France register fields require additive migration `0029_france_register.sql` before deploying the new worker.

## Deploying language-policy changes

Use a feature branch and pull request. The existing `Noracre build and tests` workflow builds the production Worker and runs the full regression suite. Merge only after checks pass for the exact reviewed head commit and confirm the base branch has not changed since verification.

Cloudflare Workers Builds deploys `main` automatically for `noracre-crm`. Verify the resulting build and deployed version against the merge commit, then check the public home page, a manually selected language, CRM login and a CRM legal page. Geographical cases are covered with trusted request metadata in the Worker tests; a client-supplied `CF-IPCountry` header does not simulate another country in production. Record the current Cloudflare version before merging for rollback. This language-policy change has no database migration or authentication changes; an application rollback can restore the preceding Worker version without undoing data.
