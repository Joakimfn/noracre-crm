# Internationalization foundation

Norwegian Bokmål is the only published language. English is a draft catalogue for the extracted UI, not a complete translation of Noracre. No language selector, browser-language detection, translated URLs, billing currency changes or country expansion is enabled by this change.

## Shared API

- lib/i18n/config.ts: locale identifiers, published locale allowlist, direction, default time zone and currency. Language does not determine billing currency or business jurisdiction.
- lib/i18n/messages/nb.ts: source messages and typed keys. en.ts must contain the same keys. Use complete sentences, named placeholders and plural objects with an other form; never build translated sentences by concatenation.
- createI18n(locale, {timeZone, currency}): request-local translator and Intl date/number/money formatters. No process-wide mutable language state. Use resolvePublishedLocale for any future user input.
- I18nProvider and useI18n: React integration. The root layout sets a deterministic Norwegian default for server rendering and hydration. A future saved preference must be resolved on the server and passed to both the provider and html lang/dir.
- t returns plain text. React escapes it; HTML templates must escape it explicitly. Do not put HTML in translation files or use translations in SQL, authorization, route IDs or database enums.
- date accepts an instant (Date or epoch milliseconds) and applies an explicit time zone. calendarDate accepts YYYY-MM-DD without shifting the day. Persist event instants as UTC ISO timestamps with an offset. Local input parsing and DST ambiguity need separate handling; do not parse translated display text with Date.parse.
- money formats the provided value only. It never converts currency. Existing prices, invoices and payment calculations remain NOK.

## Migrated starting points

CRM navigation/page headings, common follow-up date and day labels, selected number displays, HTML language/direction, and the full public enquiry form including client success/error messages use the shared infrastructure. Enquiry options submit stable identifiers; the API also accepts previously cached Norwegian values and keeps sales-email text and existing numerical-range retry fingerprints in Norwegian. Client fallback strings in public/website/site.js temporarily support cached pages without data-messages.

Existing shared CRM date helpers still use defaultI18n. They must receive the user's resolved settings before a language/time-zone selector is released. This is deliberately an incremental foundation, not a claim that every screen is translated.

## Before enabling English or another language

1. Extract remaining text in app/crm-client.tsx, components, API errors, lib/public-site.ts, public/website/site.js, emails, exports and onboarding. Keep role/status identifiers unchanged; translate their display labels through explicit mappings.
2. Complete and review dictionaries, including legal pages and business terminology. Extend message tests for each language's plural categories and placeholders.
3. Persist user language/time-zone preferences and company currency/market settings separately. Pass resolved settings through all date helpers, pickers, server messages and exports. Test server/client agreement, DST transitions, date-only fields and RTL layout where applicable.
4. Plan public locale URLs, canonical/hreflang tags and cache keys before publishing translated pages. Preserve current Norwegian URLs and Google OAuth legal-page links.
5. Review country-specific functionality separately: Brønnøysund lookup, organization numbers, phone formatting, address fields, invoicing and agreements are currently designed for Norway. Translation alone does not make these international.
6. After complete end-to-end review, add the language to publishedLocales and introduce the language selector. Do not activate the draft English catalogue on its own.

Run node --test tests/i18n.test.mjs tests/public-website.test.mjs tests/public-enquiry-runtime.test.mjs, then the normal production build. Tests cover catalogue parity, placeholders, plural forms, locale fallback, separate currencies/time zones, DST, calendar dates, React isolation/escaping and enquiry compatibility.
